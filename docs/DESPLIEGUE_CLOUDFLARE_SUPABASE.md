# Despliegue en Cloudflare Pages + Supabase

## 0. Dónde hostear: recomendación rápida

| Pieza | Servicio recomendado | Costo orientativo |
|---|---|---|
| Frontend React + PWA | **Cloudflare Pages** | Gratis |
| Backend Express + PDF/Excel | **Render** (Starter) o **Railway** | USD 7–10/mes o uso |
| Base PostgreSQL + fotos | **Supabase** (Pro para producción) | USD 25/mes aprox. |
| Dominio propio | Cloudflare Registrar o registrador | USD 10–15/año |

**Recomendación:** Cloudflare Pages + Render + Supabase. Cloudflare Pages entrega HTTPS (necesario para PWA y cámara) y el proxy evita CORS. Para pruebas iniciales se puede usar el plan gratuito de Supabase y el plan gratuito de Render, pero **Render free duerme la API** y Supabase free no está pensado para uso comercial continuo. Para el taller real, usar planes pagos o un VPS pequeño.

Si querés evitar la migración a PostgreSQL por ahora, la alternativa es desplegar **toda la app actual (Express + SQLite) en Railway o Render con un disco persistente** y usar Cloudflare Pages únicamente como frontend/proxy. Eso pone la app online rápido, pero no usa Supabase como base de datos.

## Antes de empezar: qué puede hacer cada servicio

TallerTech Manager tiene tres capas:

- **Frontend React** → sí se puede alojar en **Cloudflare Pages**.
- **API Express** → **no** se puede ejecutar en Pages tal cual. Pages aloja archivos estáticos y Pages Functions (Workers), no un servidor Node persistente con SQLite, PDFKit y sistema de archivos.
- **Base de datos SQLite actual** → **no** se puede reemplazar por Supabase solo cambiando una variable de entorno. Hay que migrar el acceso a datos a PostgreSQL.

**Supabase** ofrece PostgreSQL, Storage, Auth y backups administrados, pero no ejecuta este backend Express.

Por eso la arquitectura recomendada es:

```text
Navegador
   │
   ▼
Cloudflare Pages (React estático)
   │  /api/*  →  Pages Function proxy
   ▼
Servidor Node/Express (Render, Railway, Fly.io o VPS)
   │
   ├── PostgreSQL → Supabase
   ├── Fotos      → Supabase Storage
   └── PDF/Excel  → generados en el servidor
```

El proxy de `/api/*` ya está incluido en:

- `functions/api/[[path]].js`
- `public/_redirects`

Así el navegador ve **un solo origen** y las cookies de sesión siguen funcionando sin configurar CORS.

> **Importante:** antes de desplegar hay que completar la migración de SQLite a PostgreSQL y de fotos locales a Supabase Storage. Esta guía explica el orden exacto. La app actual sigue funcionando localmente con SQLite.

## 1. Crear el proyecto de Supabase

1. Entrar a https://supabase.com y crear un proyecto.
2. Elegir región cercana (por ejemplo, Sudamérica/Estados Unidos Este).
3. Guardar la contraseña de la base.
4. Ir a **Project Settings → Database** y copiar una cadena de conexión:
   - **Session pooler** o **Direct connection**.
   - Formato:
     ```text
     postgresql://postgres.xxxxx:TU_PASSWORD@aws-0-region.pooler.supabase.com:5432/postgres?sslmode=require
     ```
5. Ir a **Project Settings → API** y guardar:
   - `Project URL`
   - `service_role key` (solo para el backend, nunca para el frontend)

### Seguridad
- La `service_role key` **no** debe estar en Cloudflare Pages ni en el navegador.
- El frontend no habla directamente con Supabase.
- No usar la `anon key` en este proyecto si el acceso pasa por la API.

## 2. Crear el esquema PostgreSQL

El archivo actual `server/schema.sql` es para SQLite. Para Supabase hay que crear una versión PostgreSQL.

Cambios principales:

| SQLite | PostgreSQL |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `strftime('%Y-%m-%dT%H:%M:%fZ','now')` | `to_char(now() at time zone 'utc', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')` o `now()` con tipo `timestamptz` |
| `COLLATE NOCASE` | `lower(...)` o tipo `citext` |
| `PRAGMA ...` | eliminar |
| `VACUUM INTO` | backups administrados de Supabase / export JSON |
| `?` en consultas | `$1`, `$2`, ... con `pg` |
| `lastInsertRowid` | `INSERT ... RETURNING id` |
| `MAX(a, b)` escalar | `GREATEST(a, b)` |
| `date(columna)` | `(columna)::date` o `columna::timestamptz::date` |

Las tablas que deben existir son las mismas de `docs/ARQUITECTURA.md`:

`users`, `clients`, `equipment_types`, `technicians`, `orders`, `order_status_history`, `order_interventions`, `order_parts`, `order_photos`, `payments`, `products`, `product_categories`, `suppliers`, `inventory_movements`, `transactions`, `activity_log`, `login_attempts`, `settings`.

### Opciones para esta etapa
1. **Migración manual:** crear el esquema PostgreSQL en el SQL Editor y adaptar las consultas de `server/routes/` y `server/db.js`.
2. **Migración automatizada:** generar un script que lea el SQLite actual y cargue los datos en Supabase. Es el camino recomendado para no perder la información de prueba o producción.

La API debe pasar de `node:sqlite` a `pg`:

```bash
npm install pg
```

Y `server/db.js` debe usar un `Pool` de PostgreSQL:

```js
import pg from 'pg';

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: { rejectUnauthorized: false }, // según proveedor; Supabase acepta sslmode=require
  max: 5,
});

export async function all(sql, params = []) {
  const result = await pool.query(sql, params);
  return result.rows;
}
```

> El cambio a `pg` vuelve asíncronas las consultas. Hay que adaptar `get`, `all`, `run`, `insert`, `transaction` y los `await` de las rutas. No es solo cambiar el driver: también hay que revisar las consultas con funciones específicas de SQLite.

## 3. Configurar Supabase Storage para fotos

1. Ir a **Storage → New bucket**.
2. Nombre: `order-photos`.
3. Marcarlo como **privado**.
4. En el backend (Render), guardar:
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `SUPABASE_STORAGE_BUCKET=order-photos`

La lógica actual de `server/services/uploads.js` guarda archivos en `data/uploads`. En producción hay que:
1. Subir el buffer de la foto al bucket con la service role.
2. Guardar en `order_photos.file_name` la ruta dentro del bucket.
3. Al servir `/api/orders/:id/photos/:photoId`, descargar desde Storage y devolver el archivo (o generar una URL firmada temporal).

Nunca exponer el bucket como público si contiene fotos de equipos y clientes.

## 4. Desplegar la API Node

Cloudflare Pages no puede ejecutar `server/index.js`. Opciones recomendadas:

- **Render Web Service**
- **Railway**
- **Fly.io**
- **VPS con Node + PM2/systemd**

### Ejemplo con Render

1. Subir el proyecto a GitHub.
2. En Render: **New → Web Service**.
3. Conectar el repositorio.
4. Configuración:
   - **Root Directory:** `tallertech-manager` (si el repo tiene la carpeta)
   - **Runtime:** Node
   - **Build Command:** `npm ci --omit=dev`
   - **Start Command:** `node server/index.js`
   - **Node version:** 22 o 24

5. Variables de entorno:

```env
NODE_ENV=production
PORT=10000
SESSION_HOURS=12
COOKIE_SECURE=true
SEED_DEMO=false
ADMIN_USER=admin
ADMIN_PASSWORD=una-contraseña-inicial-segura
JWT_SECRET=un-secreto-largo-y-aleatorio
ENCRYPTION_KEY=una-clave-hexadecimal-de-64-caracteres
DATABASE_URL=postgresql://...
SUPABASE_URL=https://xxxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=...
SUPABASE_STORAGE_BUCKET=order-photos
WEB_ORIGIN=https://tu-app.pages.dev
WEB_ORIGIN_ALT=https://tu-dominio.com
```

6. Verificar `https://tu-api.onrender.com/api/health`.
7. Iniciar sesión vía API para comprobar que la base responde.

### Consideraciones
- Si el servidor no tiene disco persistente y las fotos van a Supabase Storage, no hace falta un disco.
- Si se mantienen respaldos JSON, conviene subirlos también a Supabase Storage o a un almacenamiento externo.
- El plan gratuito de Render puede dormir la instancia; para uso real conviene un plan pago o un VPS pequeño.
- El backend sigue generando PDF y Excel con PDFKit/ExcelJS, sin problema.

## 5. Desplegar el frontend en Cloudflare Pages

1. Subir el proyecto a GitHub (el mismo repositorio).
2. En Cloudflare: **Workers & Pages → Create → Pages → Connect to Git**.
3. Seleccionar el repo.
4. Configuración:
   - **Framework preset:** Vite (o None)
   - **Build command:** `npm ci && npm run build`
   - **Build output directory:** `dist`
   - **Root directory:** `tallertech-manager` si corresponde
   - **Node version:** 22 o 24 (variable `NODE_VERSION=24`)
5. Variable de entorno:
   ```env
   API_ORIGIN=https://tu-api.onrender.com
   ```
6. Deploy.

### El proxy `/api/*`
El archivo `functions/api/[[path]].js` ya está incluido y reenvía:

```text
https://tu-app.pages.dev/api/... → https://tu-api.onrender.com/api/...
```

Ventajas:
- El frontend sigue usando `/api`.
- No hay CORS.
- Las cookies de sesión funcionan en el dominio de Pages.
- El backend puede quedar privado detrás del proxy.

El archivo `public/_redirects` contiene:

```text
/* /index.html 200
```

para que las rutas de React (`/ordenes`, `/clientes`, etc.) funcionen al recargar.

### Custom domain
1. En Pages → **Custom domains → Set up a domain**.
2. Agregar `taller.tudominio.com`.
3. Cloudflare configura DNS si el dominio está en Cloudflare, o da el CNAME para tu proveedor.
4. Actualizar `COOKIE_SECURE=true` y probar el login por HTTPS.

### PWA y uso desde el celular

La app ya incluye:

- `public/manifest.webmanifest`
- `public/sw.js` (service worker)
- íconos de instalación
- banner **Instalar TallerTech**
- **Recepción rápida** en 3 pasos con acceso a la cámara
- guardado del borrador de recepción en el dispositivo

Cloudflare Pages publica el manifest y el service worker automáticamente porque están dentro de `public/`. No hay que configurar nada extra.

Requisitos y verificación:

1. Usar **HTTPS**. Cloudflare Pages lo entrega con el dominio `pages.dev` y con el dominio propio.
2. Desde Android/Chrome, abrir el sitio y elegir **Instalar aplicación**.
3. Desde iPhone/Safari: **Compartir → Agregar a pantalla de inicio**.
4. Verificar que abran:
   - `https://tu-dominio/manifest.webmanifest`
   - `https://tu-dominio/sw.js`
5. Probar login, recepción rápida, cámara y comprobante PDF desde el celular.
6. Si actualizás la app, el service worker toma la nueva versión al recargar. No cachea la API para no mostrar datos viejos.

> La PWA funciona en Android, iPhone, iPad, Windows y macOS. No requiere publicar en Play Store ni App Store.

## 6. Migrar datos existentes

Si ya hay datos en SQLite que querés conservar:

1. Detener el servidor local.
2. Exportar las tablas con un script de migración.
3. Insertar en PostgreSQL respetando el orden de dependencias:
   `users → clients → equipment_types → technicians → suppliers → product_categories → products → orders → order_status_history → order_interventions → order_parts → payments → inventory_movements → transactions → settings`.
4. Descargar las fotos de `data/uploads/` y subirlas al bucket `order-photos`.
5. Verificar conteos:
   ```sql
   SELECT 'clients', COUNT(*) FROM clients
   UNION ALL SELECT 'orders', COUNT(*) FROM orders
   UNION ALL SELECT 'products', COUNT(*) FROM products;
   ```

## 8. Alternativa 100 % Cloudflare (sin servidor Node)

También es posible reescribir la API como **Cloudflare Pages Functions** usando Supabase directamente, sin Render. Implica:

- Reescribir todos los endpoints de Express a Pages Functions/Hono.
- Hablar con Supabase por `supabase-js` o PostgREST.
- Migrar la autenticación a Supabase Auth o implementar JWT en Workers.
- Generar PDF/Excel en el navegador o dentro de Workers.
- Reemplazar toda la lógica de SQLite por consultas a Supabase.
- Implementar las reglas de negocio y RLS correctamente.

Es más trabajo y más riesgo que la arquitectura recomendada, pero elimina el servidor Node. Para este proyecto, salvo que el objetivo sea no tener ningún servidor, la opción Pages + Render + Supabase es la más rápida y estable.

## 9. Si querés que lo implemente en este repositorio

La migración concreta requiere:

1. Adaptar `server/db.js` y `server/schema.sql` a PostgreSQL.
2. Cambiar las consultas con sintaxis SQLite.
3. Adaptar `uploads` a Supabase Storage.
4. Agregar variables de entorno y configuración de CORS/proxy.
5. Probar login, órdenes, pagos, inventario, PDF, Excel y respaldos contra Supabase.
6. Dejar el despliegue paso a paso con los archivos listos.

No es necesario compartir la `service_role key` en el chat: se configura directamente en Render. Alcanza con indicar el **Project URL** y la **región** de Supabase para dejar la configuración preparada.
